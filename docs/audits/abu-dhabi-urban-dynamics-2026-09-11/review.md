# Abu Dhabi Urban Dynamics: review and discussion brief

11 September 2026 · Live application, deployed assets, local source, data pipeline, model mechanisms, UDES reference and interface review. Application code and published data were not changed.

The project has a useful simulation engine and unusually explicit provenance for a prototype. Its weakness is an unresolved model specification combined with an interface that exposes too much machinery. The next version needs a precise question, consistent agents and accounts, and a clear experiment workflow. A visual refresh alone would leave the main weaknesses intact.

My recommended direction is an **Abu Dhabi scenario explorer for housing, commuting and access to jobs**. Start with a bounded comparison supported by the available data; expand the scientific claim only when calibration supports it.

## What was checked

- Used the live application at 1280 × 720, opened the studio, applied Bus priority, advanced to Day 30, inspected resident and enterprise records, and explored policy, evidence, district, mobility and movement views.
- Tested arrow-key inspector tabs and keyboard selection of a map agent. Inspected a 390 × 844 phone layout. Temporary viewport overrides were reset.
- Read the worker, controller, data builder, baseline and validation materials. The downloaded live baseline matches the local baseline after JSON parsing. Important behavioral probes were repeated against the deployed, minified worker and deployed public presets.
- Checked all 18 population mappings against fresh SCAD records, all district routing anchors against polygons, and validation-report hashes against the local artifacts.
- Read the 40-page UDES v1.4 tutorial, including its equations and statecharts, and opened the original Cloud model's visual interface. This was not a full reproduction of the original model's experiments.

Detailed evidence: [data review](/F:/CODEX/Website/docs/audits/abu-dhabi-urban-dynamics-2026-09-11/data-review.md), [engine and agent review](/F:/CODEX/Website/docs/audits/abu-dhabi-urban-dynamics-2026-09-11/model-review.md), [UDES comparison](/F:/CODEX/Website/docs/audits/abu-dhabi-urban-dynamics-2026-09-11/udes-reference.md), [deployed-engine probes](/F:/CODEX/Website/docs/audits/abu-dhabi-urban-dynamics-2026-09-11/model-probes-live-output.json).

### The data is partly real, but that does not establish the results

All 18 population numeric mappings matched the intended SCAD 2024 records. That is a strength. However, jobs, salaries, rents, place quality, car ownership and supply capacities are assumed throughout the districts. Every district receives about 15% spare resident housing capacity. Bus timetables are not integrated. The nominal 2024 starting state uses geography/network sources retrieved in 2026.

The selected zones also omit relevant central and outer districts. That is a model-boundary problem, not merely a missing map layer: omitted residents and employers still contribute to real travel and housing demand.

Useful replacements already exist: [SCAD property-unit statistics](https://census.scad.gov.ae/home/realestate?lang=en), [ADREC rents and leases](https://adrec.gov.ae/en/market-data), and [Abu Dhabi Mobility timetables](https://admobility.gov.ae/en/pb-bus-service). These need matching dates, geographic units and definitions. Public downloadable GTFS availability was not established. A point inside a polygon is only an integrity check; a defensible trip origin should also represent inhabited activity or access to the network.

### The agent model needs a clearer meaning

These are real rule-based agents with persistent state and interactions. The issue is what one agent represents. Each resident agent represents 250 people, is aged 20–80, has one job status, one salary and one home rent. There are no shared household budgets, dependents or household vehicles. Population is held constant through replacement. The 600 enterprise agents are synthetic actors, not 600 observed establishments.

For an educational model, explicitly labeled representative adult groups may be enough. For affordability and relocation questions, households should have members, earners, pooled resources, tenure and housing type. For the firm's side, distinguish physical employment space, vacancies, occupied jobs and establishment cohorts. Add heterogeneity that changes decisions; more agent dots alone add little.

The employment target is enforced during hiring, and firm contraction is restricted to protect capacity. All six scenarios in the committed validation report finish at 67% employed residents and 4.28% unemployment. Those figures cannot be interpreted as independently emerging employment benefits.

Nonparticipants receive modeled support equal to their current rent plus essentials and a fixed buffer. A controlled probe increasing rent from AED 2,000 to AED 20,000 raised support by the same AED 18,000. This is a documented closure assumption, but it removes that group's financial exposure to rent increases. It should be replaced with a household resource mechanism or explicitly varied as an external assumption.

### There are concrete inconsistencies to correct

The following were reproduced against the deployed worker using controlled fixtures. They establish behavior, not the size of its citywide effect:

1. **Ownership cost:** car-acquisition affordability includes AED 700/month, but the monthly ledger does not charge that ownership obligation. Acquisition also does not book a purchase/debt transaction.
2. **Monthly accounts:** daily transport costs accumulate, while salary and rent use the final state at month close. A late separation can erase the month's salary; a late hire can receive a full month's pay. Accrue income and housing costs over spells.
3. **Financial state:** an agent can be assessed as financially normal while the accounting view reports an essentials deficit. Use the same resource definition in behavior and reporting.
4. **Relocation travel:** a same-zone destination is evaluated using the cheapest mode, a 16-minute walk under the tested defaults. Realized same-zone choices use a different probability model; the probe averaged 22.20 minutes with frequent car use. Make expectation and realized choice consistent.

### UDES is a useful conceptual reference

UDES means **Urban Dynamics Educational Simulator**. The repository currently expands it incorrectly as “Urban Dynamics for Egyptian Settlements.” The tutorial presents a toy city for teaching land-use/transport feedback and explicitly limits real-city policy use. Its simplified adult population, firm transitions and replacement mechanism are educational choices; putting them over Abu Dhabi geography does not validate their local behavior. [Correia, UDES v1.4 tutorial, pp. 3, 11–20](https://www.anylogic.com/upload/iblock/198/1985a2d61b26c2d23acd158ab6e5d68e.pdf).

Keep the inspectable decisions, spatial feedback and counterfactual experiments. Document each inherited mechanism and each local modification. The Cloud page's description and the tutorial differ on zone count, so the current upload should not be assumed to be an exact scientific specification. The original interface is also dense; it is a mechanism reference rather than a visual target.

## Interface and wording

The screenshot sequence below supports the visual findings. The live workflow works, but the primary question is hard to follow. The overview gives prominent space to 6,670 markers and four almost-empty charts on Day 0. Opening the studio adds narrow control and inspector columns, leaves a short map, and introduces multiple scrolling areas. At the observed desktop width, switching views retained the map zoom; I used Fit city to restore a useful overview.

The inspector has valuable raw material, but repeats static statements such as “What this agent is trying to do,” “UDES-style statechart,” and “Scheduled branching statechart.” An event such as “Lesser action” does not tell a reader what changed or why. The evidence panel is useful but compressed into the same narrow control column. Preserve its content in a readable Methods & data view.

| Current wording/element | Proposed treatment |
|---|---|
| Open studio | Configure scenario |
| City pulse / Live analytics | Results |
| Citizen | Resident group, until a proper household/person distinction is implemented |
| Happy / Extreme / Lesser | Plain state names tied to the measured condition; explain inherited state names in methods |
| Resident satisfaction | Modeled financial and commute stress, or separate clearly defined components |
| Peak road load | Highest modeled work-trip load; it is a maximum across links, not a peak-hour traffic measure |
| What this agent is trying to do | Replace the static paragraph with the last decision, trigger, alternatives and consequence |
| Complete agent frame | Remove from the main interface; this is rendering-status terminology |
| Repeated population, commute and satisfaction values | One authoritative result strip, with selected-area detail on demand |
| Field-provenance paragraphs everywhere | Short source badges with a direct link to the underlying assumption/source |

Keep information that changes interpretation: represented weights, whether a number is assumed, round-trip versus one-way time, units, reference year, and the comparison baseline. Cut repeated explanation of implementation internals. This needs better placement of information, not indiscriminate removal of caveats.

### Confirmed layout/accessibility issues

- **Run contrast:** its label computes to RGB(43,44,51) on RGB(14,81,74), about 1.52:1 contrast. The primary button sets white on the parent, but the site's global span rule gives the child its own dark color. See [global styles](/F:/CODEX/Website/_sass/_base.scss:194) and [primary-button styles](/F:/CODEX/Website/_sass/garden/_simulation-v2.scss:260).
- **Inconsistent type scale:** observed Run/Compare/Reset draft text is 18px while nearby tabs are 9px. Reset draft wraps into a tall heading action. The broad `font: inherit` rule on controls competes with single-class component declarations. See [control reset](/F:/CODEX/Website/_sass/garden/_simulation-v2.scss:63).
- **Crowding:** inspector facts are truncated, district labels overlap at city scale, and chart headings/axes have little room. Use a larger base UI font, a consistent control scale, resizable/collapsible panels and one main chart.
- **Responsive functionality:** below 1100px, controls are deliberately hidden and execution disabled. On phones the explanatory “not a forecast” header also disappears. A read-only mode may be a conscious scope choice, but it needs an obvious useful purpose, such as viewing a saved comparison; otherwise allow a simplified scenario workflow. See [responsive behavior](/F:/CODEX/Website/assets/js/udes-v2-app.js:5393).
- **State communication:** after a completed step the live status still carried the earlier policy-staging message. After returning from mobile size it retained the read-only announcement while desktop controls were available. Announce completed steps and restored mode concisely.

There are accessibility strengths: labeled inputs, focus styles, tab keyboard navigation, text summaries for charts, an OD data table, and keyboard map-agent selection. These checks do not establish screen-reader compatibility or full accessibility compliance. Color differentiation, target sizes, zoom/reflow and a full assistive-technology pass remain to be tested.

## Proposed experience

Use one workspace with a compact experiment header, a large map, a collapsible configuration panel and a result panel. Agent details open on selection. Methods & data opens as a readable document/panel. An optional teaching view can reveal agent state transitions in greater detail.

1. **Baseline:** display the study boundary, reference year, modeled population and evidence status. State the analytical question in one sentence.
2. **Intervention:** choose a policy, target, implementation date and amount. Review a short list of changes before applying them. Distinguish draft, scheduled and active inputs.
3. **Comparison:** run to a chosen horizon and show changes against the reference with distributions and uncertainty. Select a metric to map the change by district or group. Keep the active scenario's name visible with the charts.
4. **Explanation:** click an affected place or representative agent. Show the actual trigger, feasible alternatives, cost/time comparison, chosen action and resulting change. Expand the detailed ledger only when needed.

The existing paired reference, staged-policy handling and retained history should underpin this flow. “Compare” currently toggles reference display; make that behavior explicit. Export currently writes active history only ([controller](/F:/CODEX/Website/assets/js/udes-v2-app.js:5380)). A useful experiment export should include both runs, their differences, units, seed, model/data version, assumptions and intervention timeline. Separate export types if a compact CSV is still useful.

## Additions in a sensible order

**First milestone: make a single comparison trustworthy.** Correct spatial/financial inconsistencies, define agent units and employment closure, then test a bounded bus-service or housing-location experiment. Success means another reader can explain the chain from input to result and reproduce it.

**Next add analytical value:** distributions and group effects; jobs reachable within a declared travel time; rent burden tied to households; scenario bookmarks/exports; actual decision comparisons; repeated-seed ranges; sensitivity to influential assumptions. Expose where an answer changes sign under plausible settings.

**Then add Abu Dhabi mechanisms where the question needs them:** housing types and collective accommodation, external population/job growth, realistic bus services and transfers, lease/moving costs, staged housing delivery, walking access under heat/shade constraints, and sector-specific employment access. These should be data-backed mechanisms with testable effects.

**For costed policy comparison:** include fleet/service hours, operating costs, capital costs, road-space allocation and delivery dates. The current Bus priority bundle is a favorable change to four inputs, not a funded program. Treat scenario feasibility as a separate requirement from simulation execution.

Preserve the worker-based engine and tests. Split the very large controller/worker into explicit modules for finance, choices, network assignment, labor matching, experiments and rendering as those areas are corrected. Avoid a simultaneous framework migration: small module boundaries and stable data contracts make these changes reviewable.

## Verification and interpretation

The engine, job-capacity, history and scenario suites passed in this review. The scenario suite completed in 309 seconds and includes four ten-year presets and three paired-seed comparisons at reduced scale. The existing full-scale report's source hashes match current local artifacts, and its own wording correctly calls its checks software/regression and provisional sanity checks. It was inspected rather than regenerated. The audit's deployed-engine probes passed and reproduced the reported mechanism inconsistencies.

Further scientific work should separate software invariants, behavioral consistency, calibration and held-out validation. A fixed seed helps reproduction; it does not establish uncertainty bounds. A multi-seed reduced-agent regression test already exists, so adding full-scale uncertainty analysis would extend existing work.
